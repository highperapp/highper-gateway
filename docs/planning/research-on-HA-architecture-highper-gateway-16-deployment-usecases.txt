Mapping your 16 use cases into structured cluster personas allows users to select the right architecture based on their specific technical requirements.
## Cluster Persona Definitions

* Type A: The Edge (Independent): Focuses on raw throughput and protocol handling. No shared state is required for core operations.
* Type B: The Coordinator (Stateless+Valkey): Required for features that need a "global memory" (e.g., global rate limits, shared caches) across all nodes.
* Type C: The Trusted (Raft/Consensus): Required for sensitive configuration state where every node must be in 100% agreement (e.g., SSL certificates, service discovery). [1, 2, 3, 4, 5]

## Deployment Insights

* Kubernetes: Native support for Active-Active and Type B/C through StatefulSets and operators.
* Virtual Machines: Ideal for Active/Standby using Keepalived for a Virtual IP (VIP). Scaling is slower than K8s but more predictable.
* Bare Metal: Recommended for Type A (L4/L7 throughput) and AI/LLM Gateways (GPU access), offering up to 2x efficiency over virtualised environments. [14, 15, 16] 

## Decision Hierarchy
If a user combines multiple use cases:

   1. Rule of Thumb: The most restrictive HA logic wins. If you need Type C for certificates (03) but only Type A for TCP (01), the whole cluster must support Type C architecture.
   2. Resource Isolation: For "Mixed Mode," use Valkey Sharding to isolate high-frequency rate-limiting traffic (04) from critical AI token quotas (16) to avoid race conditions and latency spikes. [17]
